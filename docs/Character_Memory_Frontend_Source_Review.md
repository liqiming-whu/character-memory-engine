# Character Memory System / Character Memory Engine 前端源码审查总结

> ⚠️ **状态更新（2026-08-06）**：本文为源码审查阶段的假设性结论。v2.1.2 mount 实验已实锤真正根因——**Operit 每次进入插件界面重新执行整个 JS 模块 + 新模块早期工具调用返回"成功但空壳"（第二层初始化竞态）+ 空结果覆盖已有数据**。本文"生命周期 + 异步竞态"方向仍有效，但机制细节以 `docs/INIT_RACE_ROOT_CAUSE_AND_FIX_PLAN.md` 为准，修复方案按该文档执行。

## 一、审查背景

本次审查基于：

-   旧版 `character-memory-system-main` 源码
-   新版 Character Memory Engine 开发过程中的问题现象

重点分析：

-   空加载
-   快速切换界面卡顿
-   退出重新进入恢复
-   切 Tab 后恢复

目标：

判断问题主要来自：

1.  数据存储性能
2.  后端查询性能
3.  前端状态管理
4.  Operit 平台生命周期机制

------------------------------------------------------------------------

# 二、核心结论

## 结论

此前将问题主要归因于：

> JSON 读写性能不足

这个方向并不是主要原因。

原因：

旧版已经尝试：

-   拆分 JSON 文件
-   减少单文件读写

但是：

-   空加载仍存在
-   页面切换仍卡顿

同时新版：

-   SQLite
-   Worker
-   HTTP
-   sqlite-vec

已经证明后端性能足够。

因此：

## 当前主要问题：

> Operit 前端生命周期模型 + 异步状态管理设计。

------------------------------------------------------------------------

# 三、旧版源码暴露的问题

## 1. Screen 页面承担过多职责

旧版主要页面同时负责：

-   数据加载
-   记忆加载
-   UI渲染
-   状态恢复
-   自动分析
-   缓存管理

结构类似：

    Screen

    ├── 数据服务
    ├── 业务逻辑
    ├── 生命周期
    ├── 缓存
    └── UI

问题：

页面复杂度过高。

------------------------------------------------------------------------

# 四、最大问题：初始化竞态

进入页面时，会同时执行多个异步任务：

例如：

    页面加载

    ├── trigger_analysis
    ├── loadData
    ├── loadMemories
    ├── loadPersona
    └── render

多个任务：

-   调用工具
-   修改状态
-   触发渲染

可能产生：

    请求A返回

    ↓

    请求B覆盖状态

    ↓

    UI显示为空

    ↓

    重新进入恢复

------------------------------------------------------------------------

# 五、Operit 状态模型风险

## useState / useRef 与标准 React 不同

Operit 使用：

    ctx.useState(key,value)

    ctx.useRef(key,value)

带有 key。

风险：

状态可能不是普通组件生命周期。

可能出现：

第一次：

    init=true

退出页面。

再次进入：

    init仍然true

但是：

数据没有重新加载。

结果：

    初始化跳过

    UI为空

------------------------------------------------------------------------

# 六、为什么切 Tab 或重新进入会恢复？

这个现象说明：

问题不像：

-   JSON慢
-   SQLite慢
-   查询慢

更像：

    第一次渲染

    ↓

    状态没有同步

    ↓

    切换Tab触发重新渲染

    ↓

    状态重新读取

    ↓

    恢复

因此：

切换界面恢复是前端状态问题的重要证据。

------------------------------------------------------------------------

# 七、新旧版本共同问题

虽然新版改进：

-   JSON → SQLite
-   本地 Worker
-   Embedding
-   语义检索

但是前端结构仍类似：

    页面

    ├── worker调用
    ├── 数据加载
    ├── 状态管理
    ├── Tab控制
    └── UI

因此：

后端性能提升无法解决生命周期问题。

# 九、修改建议

## P0：统一状态管理

不要：

    screen

    character

    knowledge

    各自加载数据

建议：

    MemoryController / EngineStore

    ├── worker状态
    ├── 当前角色
    ├── 记忆数据
    ├── loading状态
    └── error状态

所有页面只负责展示。

------------------------------------------------------------------------

# 十、减少初始化任务数量

不要：

    进入页面

    同时：

    load persona

    load memory

    load data

    trigger analysis

建议：

    进入页面

    ↓

    确认 Engine 状态

    ↓

    加载统一数据快照

    ↓

    渲染

    ↓

    空闲后执行分析

------------------------------------------------------------------------

# 十一、避免使用 ref 控制核心流程

风险：

    initRef=true

可能跨页面保留。

不要依赖：

    是否第一次进入

控制关键初始化。

应该使用明确状态：

    engineInitialized

    workerReady

    dataLoaded

------------------------------------------------------------------------

# 十二、区分数据状态

不要使用：

    []

表示所有情况。

建议：

    null
    =
    未加载

    []
    =
    已加载但为空

    data
    =
    已加载

避免：

空数据覆盖旧状态。

------------------------------------------------------------------------

# 十三、建议验证实验

加入日志：

记录：

    时间

    页面render次数

    state值

    请求开始

    请求结束

分析空加载时属于：

## 类型A

数据没有返回。

## 类型B

数据返回，但UI没有更新。

## 类型C

初始化逻辑没有执行。

三者修复方案不同。

------------------------------------------------------------------------

# 十四、最终判断

当前项目最大的变化：

以前：

    插件开发

现在：

    本地AI应用开发

后端已经达到应用级：

-   SQLite
-   Worker
-   Embedding
-   语义检索

前端也需要升级：

从：

    脚本式页面

转变为：

    状态驱动应用

------------------------------------------------------------------------

# 总结

Character Memory System 的空加载问题长期存在，并不是因为 JSON 存储方案。

数据库和 Worker 解决的是：

-   数据规模
-   查询效率
-   语义检索

但是没有解决：

-   页面生命周期
-   状态恢复
-   异步竞态

下一阶段优化重点：

1.  单一状态源
2.  Engine 生命周期管理
3.  异步任务顺序控制
4.  Operit 生命周期适配

不要继续优化存储层。
